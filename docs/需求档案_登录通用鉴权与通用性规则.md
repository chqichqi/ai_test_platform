## R-01 登录模块 = 项目通用登录鉴权（需求定义，用户逐字确认）

### 背景

版本详情页的「导入：登录模块业务流」功能，不是普通用例导入，而是**为该项目添加一个登录鉴权的通用性登录功能**。

### 需求定义

1. **唯一登录入口**：项目内所有涉及登录的操作，**均要求必须使用该登录模块登录成功后，再进行后续操作**——包括但不限于：功能用例 → UI 用例转化、步骤驱动探索、执行测试、API 鉴权联动。
2. **转化第一用例**：从功能用例转化为 UI 用例时，**第一条要执行的用例就是 `__login__`**（按导入业务流时已转化成功的登录步骤执行）。
3. **权威来源**：`__login__` 用例的步骤数据以**导入业务流时保存的真实步骤为权威**；转化时绝不覆盖（`functional_to_ui_service.py` 转换后仅校验存在，跳过模板覆盖）。
4. **登录态复用**：登录成功 → `storage_state()` 捕获 auth_data 落 KG（`exploration_config` 凭证）→ 后续执行/探索/API 鉴权直接复用，不重复登录。

### 验收标准

- 换任意新项目：导入登录模块业务流后，转化/执行/探索自动使用该项目自己的 `__login__` 步骤（项目级隔离，`(project_id, test_case_id)` 复合唯一）
- 转化批量任务中，`__login__` 步骤严格按导入时的真实步骤执行（goto → fill 帐号 → fill 密码 → click 登录 → 机构选择 → 断言），任何一步不依赖执行器臆造
- 已导入项目重新转化时，`__login__` 不被模板覆盖

### 实现位置

- 统一入口：`backend/app/core/services/login_engine.py` `login_with_ui_case`
- 导入生成：`backend/app/core/services/functional_to_ui_service.py` `import_login_module`
- 转化首用例：`_explore_by_steps_async`（登录 → storage_state → 同步探索 9 模块）

## R-02 登录流程执行 = 步骤数据驱动 + 反射分发（用户要求，2026-08-16）

### 背景

用户批评：「你为什么会把用例中的内容写到代码中呢？万一，是另一个项目的登录模块变化了呢？你应该是从登录UI用例中读取步骤数据进行参数化通过反射机制进行调用这个步骤进行执行测试呀」——执行器把医院系统机构卡片选择器、确认按钮文字写死在 `login_engine.py`。

### 需求定义

1. **步骤数据自包含**：登录 UI 用例的每个步骤 `args` 承载全部定位参数（url/placeholder/locator/css/role/cards_selector/confirm_text…），执行器只读参数执行，不造参数。
2. **反射分发**：执行器按 action 名从 dispatch 表取 handler 调用（`_LOGIN_HANDLERS`），新增 action 类型只需注册 handler，主循环不改。
3. **自学习回填**：导入验证（StepRunner）真实跑通机构页后，把实际用到的定位参数回填进 `handle_org_selection` 步骤 args——换项目 = 重新导入 = 数据自动更新，代码零改动。
4. **同源策略**：同一 action 的多个执行器（StepRunner / login_with_ui_case / LoginEngine）共用同一套「参数优先 → 通用兜底」逻辑，禁止分叉。

### 验收标准

- `__login__` 用例数据中不存在「写死选择器」的执行器；全部定位参数可从用例步骤数据查到
- 换一个登录流程完全不同的项目：只需重新导入登录模块业务流，平台代码零改动
- 旧数据（args 缺失的历史用例）仍可执行（通用兜底候选），但新导入项目不依赖兜底

### 实现位置

- `login_engine.py`：`_LOGIN_HANDLERS` 反射分发表 + `_h_*` handler 系列
- `step_runner.py`：`_do_handle_org_selection` 参数化 + `self._org_meta` 自学习记录
- `functional_to_ui_service.py`：导入阶段三验证成功后回填 `_org_meta` 到步骤 args

## R-04 登录模块跨项目通用性（用户 2026-09-02 重申固化）

> 用户原话：「创建项目后，每个项目的登录模块都必须要是通用的。即不要将来重新创建了一个新项目，其登录业务流变化，也应该能正常登录哈。同时所有代码中绝对不能存在硬编码。」

### 需求定义

每个项目的登录模块必须**跨项目通用**：换一个新项目、登录业务流完全不同，只要**重新导入该项目的登录模块业务流**，就必须能正常登录，**平台代码零改动**。所有代码中绝对不能存在硬编码。

### 验收标准

1. 新建任意项目 → 配置 base_url/登录账号/密码 → 导入该项目登录模块业务流 → 自动识别真实登录页元素 → 登录成功（含机构选择等后续流程）→ **平台代码零改动**
2. 换一个登录流程完全不同的新项目 → 重新导入 → 依然能正常登录
3. 全仓检索不到被测系统登录相关选择器/按钮文字/路由/URL 关键字（豁免清单除外）；登录元素识别/执行/探索/API 鉴权联动全部数据驱动

### 实现机制（与 R-01/R-02/R-03 同源，细则见 `RULES.md` 一·五节 + 二节）

- 步骤数据自包含 + 反射分发 + 自学习回填（换项目 = 重新导入 = 数据自动更新，代码零改动）
- 元素识别 / 文本匹配统一去空白归一化 `normalize_ws`（不针对任何具体文案）

### 关联修复沉淀（2026-09-02）

- `_rule_pick_login_elements` 元素识别关键词匹配统一 `normalize_ws` 去空白（真实按钮「登 录」匹配「登录」失败 → 三要素识别 None → 无法点击登录），与执行侧 StepRunner 同源 —— 详见 `RULES.md` 历史教训档案 2026-09-02 行

## R-05 测试执行 = pytest 参数化 + 反射机制（用户 2026-09-02 强调固化）

> 用户原话：「我们项目将来的测试是使用 pytest 的参数化，以及通过反射机制进行调用呀。」

### 需求定义

所有测试执行统一走「**pytest 参数化 + 反射分发**」：
1. 在线执行（`run_parametrized_specs`，spec 全量参数化含 preconditions）与生成的 pytest 工程（`build_pytest_project` → `@pytest.mark.parametrize("spec", load_all_specs())`）**同构同源**
2. 步骤执行按 action 名从 dispatch 表**反射取 handler**（StepRunner `builtins`/`_do_*` 表、login_engine `_LOGIN_HANDLERS`），新增 action 类型只注册 handler，主循环不改
3. 禁止为每条用例写死独立函数/线性脚本；同一 action 的多执行器禁止分叉

### 实现位置

- `step_runner.py`：`run_parametrized_specs`（在线参数化执行）/ `build_pytest_project`（生成 pytest 工程）/ StepRunner `_do_*` 反射 dispatch
- `login_engine.py`：`_LOGIN_HANDLERS` 反射表
- 规则细则：`RULES.md` 二.7（通用性设计原则）
