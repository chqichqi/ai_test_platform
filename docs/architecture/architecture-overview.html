1总体框架（端到端用例生产管线）

八步全流程主链路（导入 → 功能用例 → UI 用例 → 场景编排 → 执行 → 报告 → CI/CD → 反馈），是"需求 → 可跑用例 → 跑完闭环"的主干；围绕它展开服务、探索引擎与执行器。

① 导入
需求/业务流文档按日期块追加到版本（不覆盖）；登录模块为项目级单独管理
→
② 功能用例
AI「先理解成规范模型再生成」：Step1 整篇理解出模块共享声明；Step2 按模块注入逐条生成（含前置/依赖模型）
→
③ UI 用例
功能→UI 转化：步骤解析「」标记 → 真实探索/查 KG → 生成 spec 落库
→
④ 场景编排
把生成用例按真实业务编成场景：加入用例、拖拽重排顺序、单条启用/禁用，组成可复用的回归路径
→
⑤ 执行
执行中心一键跑：依赖调度(前置先跑/共享去重/失败即跳) + 多策略定位 + 断言；失败自动截图留日志
→
⑥ 报告生成
执行结果按成功/跳过/失败汇总成报告，可查看、可追溯单条失败
→
⑦ CI/CD 集成
对接 Jenkins / GitLab 触发自动执行、回传结果(设计含于此链)
→
⑧ 结果反馈与通知
结果反馈进问题跟踪/失败分析形成闭环；站内结果已支持；飞书/钉钉等外部渠道推送规划中

技术分层

  • 前端 React SPA → 后端 FastAPI 服务层 → AI Agent / 业务服务 → 浏览器与外部被测系统。
  • 登录模块（项目级）：数据驱动 + 反射分发，贯穿探索/执行/API 鉴权，换项目重导入即登录。
  • 关键链路先落 docs/architecture 方案再写代码；共享规则一律 import 同源。

执行与数据层

  • 测试数据体系：由专门模块按 data_plan 执行期生成并注入（详见下方「重点」）。
  • 探索结果落 KG（页面/元素/URL/API），作为转化与执行的真值来源。
  • 统计口径：只算用户选中用例；execution_type 区分 UI 验证 / 场景测试。

重点 · 测试数据如何生成、如何关联到用例（专门的测试数据体系）

平台内置一套独立的测试数据生成体系（数据计划 + 生成器 + Provider 注册表 + Manager），职责是：数据到底怎么生成、值从哪来——不让 LLM / 自动化脚本临场编造，也不把某次运行的随机值当成长期资产写死。核心链路为 定义数据计划 → 执行期实例化生成 → 渲染注入用例 → 跨用例传递。

🗒

① 数据计划：声明"需要什么数据"

  • 生成功能用例时，数据计划(data_plan)由生成 Agent 一并产出：描述该条用例需要哪些字段及其生成策略（如 patient_name：type=generated、provider=generator、generator=name）。
  • 规则明确：data_plan 只描述"要什么"，不把一次运行产生的随机值写死为长期资产；数据引用在步骤里用 ${key} 占位。
⚙

② 执行期：数据模块真正生成

  • 执行时 TestDataManager.build_plan → materialize，把数据计划实例化成真实值。
  • TestDataGenerator 按字段 key 自动推断类型（phone / email / 姓名 / 日期 / id / uuid…），也可 register 自定义生成器。
  • Provider 注册表决定值来源：static / shared / generated / seeded / factory / dependent / consumable，统一从注册表取、可追溯来源。
🔗

③ 渲染注入 + 跨用例传递

  • 生成值写入运行时变量后，渲染器把用例步骤 / 请求体里的 ${key} 替换成真值再执行，保证同一次运行内数据一致。
  • 执行结果也把运行值写回审计（runtime_test_data / run_id），可溯源本次跑用的是哪个值。
  • UI 与 API 用例共用同一套 Manager；API 异常/边界值由 mutation provider 确定性生成。
一句话：LLM 只在生成时定义"这条用例需要什么数据"（数据计划），具体值由专门的测试数据模块在执行时按类型确定性生成、并按 ${key} 注入对应步骤；动态业务数据是否出现则用守卫动作容错。

3关键技术难点与应对（支撑"可信"）

难点① 自然语言 → 正确用例

  • 语义 ≠ 格式：先理解成规范模型（模块/入口导航/共享前置/断言），不枚举格式。
  • 容错不静默：分块 + 每批拆半重试到单点；坏响应显式记录，绝不静默漏卡。
  • 落库净化闸：整条菜单/跨模块按钮塞进对象标记的脏文本，入库前自动裁剪。

难点② 前置条件 vs 入口导航

  • 前置条件从不执行，只写真实静态就绪态，不含操作动词。
  • 入口导航必须是 test_steps 第 1 步（不是「已处于 XX 页」），漏写时按模块声明确定性兜底前插。

难点③ 功能 → UI 不靠猜

  • 真值 ≠ 声称：URL/跳转只来自真实探索，匹配不到转「等渲染」，绝不编造 goto。
  • 多策略定位 + 叶子优先：role/文本/占位/CSS/XPath 评分，命中容器自动选最小可操作叶子。
  • 探索边界两难：只放行用例真实可达的同源页，拦误点、不误伤合法跨模块跳转。

难点④ 执行可信 / 数据关联

  • 测试数据随用例走：语义样本 + 运行时变量注入 + 跨用例产出传递。
  • 动态数据不硬等：守卫动作有则继续/无则跳过；统计只验结构不验数值。
  • 不假绿：guard 找不到数据=跳过，普通 click/断言找不到=失败。

4贯穿始终的设计原则

🧱 跨项目通用 · 零硬编码

  • 被测系统的选择器/文案/URL/魔法数字一律进「数据位」（步骤 args / 探索配置 / 项目设置），代码位永不写死。
  • 换任何被测系统、换登录流程，平台代码零改动即可复用。

🧾 可核查溯源 · 宁缺毋假

  • 从需求 → 用例 → 探索真值 → 执行结果 → 失败分析，数据一路留痕，能往回追。
  • 依赖真实探索真值的 URL/元素宁缺毋假、不编造；本页已实现/未实现如实标注。
一句话：把写用例、排顺序、对结果、查失败的重复劳动自动化率提上去；省下的时间用来做更有判断力的事——审用例、补边界、盯真回归。

5对测试人员的价值（提质 · 增效 · 解决问题）

🎯

提质 · 测得更可信

  • 用例不是编的：UI 用例的页面/元素/跳转 URL 来自平台真实打开被测系统探索的结果，能跑才算数。
  • 覆盖全、不漏卡：AI 按需求逐点生成并自动核对数量，缺了补、坏了重试，不静默漏功能。
  • 结果不假绿：严格区分"数据没出现(跳过)"与"真出 bug(失败)"，不把没跑当通过。
⚡

增效 · 测得更省力

  • 自然语言→用例：丢一段需求/业务流，自动产出规范化功能与 UI 用例。
  • 跨项目复用：换被测系统只重导入需求+登录流程，代码零改动。
  • 依赖自动调度：前置/共享准备自动先跑、共享去重，免人工排顺序。
  • 定位免维护：多策略定位 + 自动兜底，常见文案/结构微调不立刻全挂。
🛠

解决问题 · 知道错在哪

  • 失败不抓瞎：自动截图+日志，AI 做根因分析，从"红了"到"为什么红"。
  • 问题可跟踪：失败→分析→建问题→修复→回归，形成闭环有据可查。
  • 死角有兜底：自动进不去的页面，规划手动探索补录。

8规划 / 演进中的能力

这些能力方向已明确、设计要点已定，但目前尚未完全实现，如实列出供了解。

🖱

手动探索（自动探索补盲 · 规划中）

  • 解决什么：自动探索被权限/口令/验证码挡住的子页面进不去，导致这些模块没有真实真值。
  • 打算怎么做：页面点「手动探索」→ 打开受控录制浏览器，人真实操作一遍，平台捕获成结构化探索记录。
  • 要点：录前先选/归模块名；保存前按「页面+对象」查重 —— 同对象则替换、无则追加；作为自动探索的兜底。
🔁

元素自愈 L2 / L3（推进中）

  • 已有：多候选回退 + 定位可见超时的时序重试。
  • 规划四层：确定性回退链 → 属性指纹评分 → LLM 语义兜底 → 失败根因分组。
  • 铁律：只修「定位失败」，不修断言/业务/数据失败（避免误 heal 真回归、假绿）；高置信自动应用、模糊转人工审批。
🔌

CI/CD 集成 + 告警通知（未实现）

  • 说明：方向明确，尚未接入真实 CI/CD 与通知渠道。
