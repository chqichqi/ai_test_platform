## 0. 适用范围

本 SKILL 覆盖两种自然语言输入的统一处理标准：

| 输入类型 | 来源 | 典型特征 |
|---------|------|---------|
| 业务流描述 | SkillInput / 手动编写 | 操作步骤风格，偏 UI 交互，含具体元素名 |
| 需求文档 | 上传的 PRD / 规格说明 | 功能描述风格，偏业务逻辑，含场景规则 |

[MUST] 两种输入统一走本规范。

## 1. 角色与领域知识

### 1.1 角色设定
[MUST] LLM 被设定为该领域的资深功能测试专家，精通被测系统的各模块功能。

### 1.2 领域知识注入
[MUST] 系统 prompt 必须包含：被测系统类型、主要模块列表、现有 Page Object 能力摘要、该系统特有的业务规则。

---

## 2. 测试设计方法论（强制）

[MUST] 生成用例时必须系统性地运用以下四种方法：

### 2.1 场景法（Scenario Testing）
- 基于业务流程设计端到端测试场景
- [MUST] 每个业务流至少 1 条端到端场景用例

### 2.2 边界值分析（Boundary Value Analysis）
- [MUST] 覆盖：最小值-1 / 最小值 / 最大值 / 最大值+1 / 空值/0值

### 2.3 等价类划分（Equivalence Partitioning）
- 每个互斥选项类别至少取一个代表值
- 涉及选项组合时，核心组合必须保留

### 2.4 错误推测法（Error Guessing）
- [MUST] 覆盖：网络异常、权限不足、数据不存在、并发冲突、特殊字符

---

## 3. 用例设计规范

### 3.1 覆盖度要求
[MUST] 每个功能点至少包含：
- **1 条正向用例**（Happy Path）
- **1 条反向用例**（异常输入/非法操作）
- **1 条边界用例**（边界条件/极限值/空状态）

### 3.2 用例标题
[MUST] 格式：`{模块}-{功能点}-{场景描述}`，不超过 50 字。

### 3.3 前置条件
[MUST] 明确描述：登录角色、所在页面、数据准备、环境状态。

### 3.4 测试步骤（原子化）
[MUST] 每条步骤是单一不可再分的原子操作：
- ✅ 正确：「点击'新增患者'按钮」
- ❌ 错误：「测试新增患者功能」

### 3.5 预期结果（可验证）
[MUST] 必须是具体可观测的状态变化：
- ✅ 正确：「弹窗标题显示'新增患者'」
- ❌ 禁止：「测试通过」「功能正常」「操作成功」

### 3.6 优先级定义
- P0：核心流程，阻塞性缺陷
- P1：重要功能，影响主要用户
- P2：一般功能
- P3：边缘场景

---

## 4. 拆分规则（强制）

### 4.1 并列选项拆分
[MUST] 涉及"多个并列选项/类型/科室/状态"时，拆分为多条独立用例：
- "筛选不同科室" → 拆为 N 条：「筛选-心内科」「筛选-神经内科」
- "下拉选项(全部/≥10/≥20)" → 每条一个选项
- "多个预警类型" → 每个类型一条

[MUST NOT] 将多个并列场景合并到一条用例中遍历。

### 4.2 模块拆分
[MUST] 跨模块功能拆分为多条用例，每条只属一个模块。

### 4.3 权限/角色拆分
[MUST] 多角色场景下，同功能不同表现 → 拆分为多条独立用例。

---

## 5. 输出契约 —— 每条功能用例的必需要素

[MUST] 每条功能用例必须包含以下全部字段，缺一不可。

### 5.1 字段定义表

| # | 字段 | 必填 | 类型 | 说明 | 示例 |
|---|------|------|------|------|------|
| 1 | `module` | ✅ | string | **所属模块**：被测系统的实际模块名，不能为空或"通用"。一个用例只属一个模块 | `"患者档案"` |
| 2 | `title` | ✅ | string | **用例标题**：格式 `{模块}-{功能点}-{场景描述}`，不超过 50 字，一眼看出测试对象和场景 | `"患者档案-姓名搜索-输入不存在的姓名"` |
| 3 | `precondition` | ✅ | string | **前置条件**：明确描述登录角色、所在页面、数据准备、环境状态。禁止写"无"或空字符串 | `"已以医生角色登录，进入患者档案页面，系统中已有至少 3 条患者记录"` |
| 4 | `priority` | ✅ | string | **优先级**：`P0`(核心流程/阻塞性)、`P1`(重要功能)、`P2`(一般功能)、`P3`(边缘场景) | `"P1"` |
| 5 | `case_type` | ✅ | string | **用例类型**：`smoke`(冒烟)、`functional`(功能)、`regression`(回归)、`boundary`(边界) | `"functional"` |
| 6 | `steps` | ✅ | array | **测试步骤**（有序）：每一步包含 `seq`(序号,从1递增)、`action`(操作描述)、`expected`(预期结果)。步骤数3-15，禁止模糊描述 | 见 5.2 |
| 7 | `expected_result` | ✅ | string | **整体预期结果**：整个用例执行完成后的最终结果。与 steps 中每步的 expected 不同——后者是单步结果，这里是整条用例的最终判定 | `"搜索结果显示'暂无数据'，页面无报错"` |
| 8 | `tags` | ✅ | array | **标签**：至少 1 个，建议 2-4 个。用于分类和筛选 | `["患者档案","搜索","反向用例"]` |
| 9 | `test_data` | ✅ | object | **测试数据**：本条用例使用的具体测试数据值。若无特殊数据值，写空对象 `{}`。禁止写"任意"或"无" | `{"name":"张三","phone":"13800138000"}` |

### 5.2 测试步骤（steps）的每项子字段

| 字段 | 必填 | 说明 |
|------|------|------|
| `seq` | ✅ | **步骤序号**：从 1 开始递增，有序排列（1, 2, 3, 4...） |
| `action` | ✅ | **操作描述**：原子化的 UI 操作，如"点击'新增患者'按钮""在姓名框输入'张三'""选择科室下拉-心内科" |
| `expected` | ✅ | **单步预期结果**：本条操作完成后立即可观测的状态变化，如"弹窗标题显示'新增患者'""URL 包含 /patient""表格刷新，显示筛选后的数据" |

### 5.3 完整示例

```json
{
  "test_cases": [
    {
      "module": "患者档案",
      "title": "患者档案-姓名搜索-输入存在的患者姓名",
      "precondition": "已以医生角色登录系统，进入患者档案页面，系统中已有患者'张三'的记录",
      "priority": "P1",
      "case_type": "functional",
      "steps": [
        {"seq": 1, "action": "定位搜索区域的姓名输入框", "expected": "姓名输入框显示在搜索栏中"},
        {"seq": 2, "action": "在姓名输入框中输入'张三'", "expected": "输入框显示'张三'"},
        {"seq": 3, "action": "点击'查询'按钮", "expected": "页面刷新，表格中显示查询结果"},
        {"seq": 4, "action": "检查表格中的患者姓名列", "expected": "表格中至少1条记录，姓名列包含'张三'"}
      ],
      "expected_result": "成功搜索到患者'张三'的记录，表格数据正确展示",
      "test_data": {"search_name": "张三"},
      "tags": ["患者档案", "搜索", "正向用例"]
    },
    {
      "module": "患者档案",
      "title": "患者档案-姓名搜索-输入不存在的患者姓名",
      "precondition": "已以医生角色登录系统，进入患者档案页面",
      "priority": "P2",
      "case_type": "regression",
      "steps": [
        {"seq": 1, "action": "定位搜索区域的姓名输入框", "expected": "姓名输入框显示在搜索栏中"},
        {"seq": 2, "action": "在姓名输入框中输入'不存在的患者XYZ'", "expected": "输入框显示输入内容"},
        {"seq": 3, "action": "点击'查询'按钮", "expected": "页面刷新"},
        {"seq": 4, "action": "检查搜索结果区域", "expected": "表格显示'暂无数据'或结果数为0"}
      ],
      "expected_result": "页面提示'暂无数据'，无报错信息",
      "test_data": {"search_name": "不存在的患者XYZ"},
      "tags": ["患者档案", "搜索", "反向用例", "边界"]
    }
  ]
}
```

### 5.4 case_type 使用规范

| 类型 | 何时使用 | 典型优先级 |
|------|---------|-----------|
| `smoke` | 冒烟测试——核心流程最简路径，验证系统基本可用 | P0 |
| `functional` | 功能测试——正向功能验证，Happy Path | P1/P2 |
| `regression` | 回归测试——曾出过 Bug 的场景、反向用例、异常处理 | P2 |
| `boundary` | 边界测试——边界值、空值、极限值、极端组合 | P3 |

### 5.5 常见错误对照

| ❌ 错误写法 | ✅ 正确写法 |
|------------|------------|
| `"precondition": "无"` | `"precondition": "已以医生角色登录系统，进入工作台页面"` |
| `"expected": "测试通过"` | `"expected": "页面跳转至患者档案，URL包含/patientarchieve"` |
| `"expected": "功能正常"` | `"expected": "弹窗关闭，列表页面刷新，新患者'张三'出现在表格第一行"` |
| `"action": "测试搜索功能"` | `"action": "在搜索框输入'张三'，点击查询按钮"` |
| `"test_data": {}`（业务需要数据却不填） | `"test_data": {"name":"张三","department":"心内科"}` |
| `steps` 只有 1 步 | `steps` 至少 3 步（定位→操作→验证） |

## 6. 反模式（禁止）

| ID | 反模式 | 级别 |
|----|--------|------|
| FC001 | expected 仅写"测试通过""功能正常" | **block** |
| FC002 | 步骤写成代码级操作 | **block** |
| FC003 | 步骤过于抽象 | **block** |
| FC004 | 一条用例遍历多个并列选项 | **block** |
| FC005 | 使用 CSS 选择器或 XPath | **block** |
| FC006 | 标题不含模块名或场景 | **block** |
| FC007 | 步骤缺少预期结果 | **block** |
| FC008 | 前置条件不明确 | warn |
| FC009 | 标签为空或无关 | warn |
| FC010 | 多个功能点合在一条用例 | **block** |

## 7. 去重与更新策略

### 7.1 标题去重
- 完全匹配 → 更新已有用例
- 近似匹配（>80%）→ 更新+日志标注
- 无匹配 → 新建

### 7.2 版本管理
[MUST] 更新已有用例时：版本号+1、状态回退 draft、关联 UI 用例标记 needs_regeneration。

---

## 8. 质量门禁

| # | 检查项 | 不通过行为 |
|---|--------|-----------|
| 1 | 用例数 ≥ 功能点数 × 2 | 标记 warning |
| 2 | 每条用例步骤数 ≥ 3 | 剔除 |
| 3 | expected 不含模糊词 | 标记 pending_review |
| 4 | 无 title 重复 | 去重 |
| 5 | 至少 1 条 P0（若有核心流程） | 无需处理 |
